# Competencias transversales de Secundaria

Admin configura `tutorAulas` dentro de la configuración vigente `DOCENTE_ACCESOS`. Solo puede existir un tutor activo por aula. Guardar docentes incrementa `permisosVersion` y revoca las sesiones docentes anteriores; deberán ingresar nuevamente. La firma y duración de 12 horas no cambian.

Registro permite aportar ambas competencias desde cada área curricular autorizada mediante fecha/sesión → competencia → una o varias capacidades → grilla por estudiante → guardar el bloque completo. Se pueden consultar y modificar sesiones anteriores del bimestre abierto; eliminar una capacidad elimina sus notas de la versión vigente, conservando las versiones append anteriores. La grilla utiliza letras o números de 0 a 20. Valida primero el rango 0–20 y normaliza las notas numéricas a entero mediante Math.round(), igual que Registro; conserva ese número normalizado y su equivalencia: 18–20 AD, 14–17 A, 11–13 B, 0–10 C. La antigua área Competencias Transversales deja de ofrecerse en nuevas asignaciones de Secundaria; sus datos anteriores se conservan sin migración. Primaria mantiene su modelo vigente.

El módulo `transversales.html` permite al tutor consultar únicamente sus aulas y a PIP/AIP coordinar Secundaria. Admin consulta todo sin sustituir las confirmaciones. Los docentes que no son tutores solo reciben sus propios aportes del área/aula consultada en Registro. Las lecturas entregan un padrón mínimo del aula y bimestre; PIP no obtiene acceso a `loadstudents`.

Primero cada área obtiene, por separado para TIC y aprendizaje autónomo, un resultado bimestral desde las evidencias. El criterio coincide con `notaDesdeSesiones` de Registro: letras a 19/15/12/8, promedio de las notas disponibles y Math.round(), seguido del nivel AD/A/B/C. Una competencia sin ninguna nota válida queda Sin aporte; no se exige calificar todas sus capacidades. La grilla muestra por estudiante evidencias registradas, capacidades trabajadas y resultado del área.

El núcleo `registro-evaluation.js` reúne capacidades oficiales y cálculo; la misma función se incluye en el backend completo. Una prueba exige igualdad exacta frontend/backend y otra compara resultados contra la función real de Registro. Las funciones académicas existentes permanecen intactas.

La sugerencia cuenta una valoración por área y propone únicamente un nivel modal sin empate. Empates, diferencias de dos niveles y áreas faltantes generan una alerta informativa. El tutor o AIP introduce explícitamente la decisión final. Debe justificarla si difiere de la sugerencia, no existe sugerencia o hay alerta. Ninguna sugerencia se transforma automáticamente en nota oficial.

Cada competencia requiere confirmación independiente de Tutor y AIP sobre la decisión vigente. Cambiar la decisión o su justificación retira ambas confirmaciones. Cambiar cualquier evidencia —sesión, capacidad, nota o eliminación— incrementa la versión del aporte y exige nueva confirmación incluso si el nivel bimestral continúa igual. Cambiar cualquier aporte, la configuración académica relevante de esa aula o la versión del padrón vuelve obsoleta la decisión anterior y exige revisarla, guardarla y confirmarla nuevamente. Los bimestres cerrados/bloqueados son consultables, sin escrituras.

## Almacenamiento y transporte

Las hojas privadas `TransversalesAportes` y `TransversalesConsolidado` se crean al primer guardado y conservan versiones por append. No se reescribe `RegistroNotas` ni se transforman notas históricas. Los aportes están separados por bimestre, aula, área y usuario. El JSON schema 1 guarda `sessions`, `grades` y `finales` calculados exclusivamente por servidor; cada nota se asocia a fecha + competencia + capacidad + identidad del estudiante. El backend valida fecha/capacidad/estudiante y reconstruye área, aula, bimestre, usuario, docente y timestamps desde la sesión/configuración vigente. Tutor/AIP dispone de Ver evidencias por área, solo lectura. Los anteriores aportes directos se conservan como legacy, sin convertirlos automáticamente en evidencias ni votos; el prefijo de versión evidencias-v1 hace obsoletas las confirmaciones del modelo previo sin borrar decisiones. El consolidado conserva equivalencia, valor original, justificación, autor, fecha, resumen pedagógico y ambas confirmaciones. Los bloques que superan 45.000 caracteres se guardan en filas de partes y un marcador final, para respetar el límite de una celda de Sheets. Se publican solo al completar las partes; un guardado interrumpido no sustituye la versión anterior. No guarda tokens ni contraseñas.

La versión de aportes combina una huella SHA-256 determinista de las relaciones área/usuario/aula y tutor de ese contexto con la versión real de aportes y del padrón. Excluye contraseñas, nombres, cambios en otras aulas y docentes de Primaria; el orden del JSON no altera la huella. La revocación de tokens por permisosVersion continúa siendo independiente.

Las escrituras se serializan con ScriptLock y comprueban versión esperada. Una edición concurrente devuelve `CONFLICT` para recargar y revisar; no se reintenta una escritura automáticamente. Las lecturas se deduplican por token y contexto en memoria.

El bridge específico `transversales-v1` utiliza HtmlService + google.script.run y comparte las validaciones de origen, ventana y nonce del bridge vigente. Su RPC acepta únicamente las siete acciones del módulo. El token viaja por postMessage/cuerpo POST y nunca por URL. Si no se establece el bridge se usa el POST existente; cuando está listo no se duplica la petición. Las respuestas se descartan si cambia el token. El Service Worker v10 almacena solo recursos estáticos; ningún aporte, padrón ni decisión entra en CacheStorage.

## SIAGIE y operación

Cada decisión conserva dos campos separados: `justificacion` explica la decisión colegiada con las mismas reglas anteriores; `conclusion` describe el aprendizaje del estudiante para SIAGIE. En Secundaria, únicamente el nivel C exige una conclusión descriptiva no vacía. Puede guardarse como borrador sin ella, pero ni Tutor ni AIP pueden confirmarlo y nunca aparece listo para SIAGIE, incluso si un registro antiguo tiene ambas confirmaciones. Cambiar la conclusión retira ambas confirmaciones y exige confirmarlas nuevamente. En DESEN TIC / GEST AUTO, el nivel C exporta exclusivamente `conclusion`; nunca utiliza `justificacion` como reemplazo. AD/A/B no requieren conclusión.

En Admin, DESEN TIC y GEST AUTO utilizan únicamente finales con ambas confirmaciones y versión vigente. Se limpian las celdas transversales antes de asociar cada fila al padrón. Las filas identificadas que no se vinculan inequívocamente quedan pendientes; las vacías no generan pendientes y se informa cada estudiante/competencia pendiente. Si hay pendientes, antes de descargar se solicita confirmación explícita para generar un archivo parcial; cancelar no descarga nada. El archivo aceptado se identifica como parcial y NO listo para envío completo a SIAGIE. Solo un consolidado completo, vigente y confirmado se presenta como Registro oficial listo. Se comprueba de nuevo la versión antes de generar el archivo. Las hojas académicas mantienen su exportación existente.

El backend completo y compacto está en `apps-script/Codigo.js`. Este PR no ejecuta merge ni deploy. Después de revisión y autorización se necesitará actualizar Apps Script con ese archivo completo y una nueva versión de la implementación existente, manteniendo su URL. La validación local no sustituye la comprobación posterior en producción.
